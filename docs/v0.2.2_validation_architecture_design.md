# AI Scientific Data Assistant v0.2.2 Validation 架构设计

## 1. 文档目的

v0.2.1 已将默认视觉识别流程切换为 Extraction：首轮模型只负责把图片中直接可见的实验记录提取为结构化观察数据，减少长 JSON 截断风险。

v0.2.2 的目标是在 Extraction 之后增加独立的 AI Validation（数据检查）阶段：检查结构化数据中的潜在问题，向用户提供可追溯的提示和建议，但绝不修改 Extraction 产生的原始观察数据。

本设计只描述架构，不修改现有代码、Prompt、UI、Excel 或数据模型。

## 2. 设计原则

Validation 必须遵守以下优先级：

1. Extraction 的观察结果是只读输入。
2. Validation 只能发现问题和提出建议，不能删除、合并、补写或覆盖数据行。
3. AI 建议必须等待用户明确接受，才能成为最终确认值。
4. Validation 失败、超时或返回无效 JSON 时，Extraction 结果仍然可查看、确认和导出。
5. 所有发现必须尽量绑定到明确的行和字段；无法定位时保留为全局警告，不能猜测位置。
6. 缺失值仍是缺失值。除非存在明确依据并经用户确认，否则不得生成实验测量数据。
7. 模型置信度只是提示信息，不能作为自动修改数据的授权。

## 3. Validation 的目标与边界

### 3.1 负责内容

Validation 最小版本负责：

- **异常检测**：提示编号格式异常、明显不符合上下文的字符、数值格式异常和可疑极端值。
- **缺失提醒**：提示缺失字段、缺失单位、重复编号不完整或某行关键值为空。
- **数据一致性检查**：检查同列数据类型、处理编号分段结构、重复实验元数据和字段单位是否一致。
- **可疑值提示**：对可能由识别错误造成的字符、数字、小数点或符号提出候选建议。

### 3.2 不负责内容

Validation 不应：

- 修改 `observed_values` 或 Extraction 的 `rows`；
- 自动把 `suggested_value` 写入 `final_value`；
- 删除疑似错误或空缺的数据行；
- 自动填补真实实验测量值；
- 自动计算平均值、标准差或显著性；
- 在 v0.2.2 中执行变量自动排序、单位换算或复杂实验设计推断；
- 声称某个异常一定是实验错误。

### 3.3 数据检查与图片复核的区别

最小 Validation 以 Extraction 产生的 `ExperimentResult` 为主要输入，适合检查结构、缺失和上下文一致性。

仅凭结构化数据无法可靠判断“图片中的原字符到底是什么”，也无法证明 Extraction 是否漏掉了图片中的整行。未来可以增加可选的图片复核模式，把原图与目标行位置一起发送给视觉模型；该能力应作为后续增强，不能与最小数据检查混为一谈。

## 4. 输入设计

### 4.1 必需输入

Validation 接收 Extraction 产生的 `ExperimentResult`，但发送给模型时应构造精简、只读快照，而不是直接序列化整个 Python 对象。

建议输入内容：

```json
{
  "columns": [
    {
      "internal_name": "treatment_id",
      "display_name": "处理编号",
      "original_unit": null
    }
  ],
  "observed_rows": [
    {
      "row_index": 1,
      "values": {
        "treatment_id": "S0/L/E+/N2",
        "measurement": "4.58"
      },
      "replicate_group": null,
      "replicate_index": null
    }
  ],
  "existing_warnings": []
}
```

输入规则：

- `row_index` 使用页面展示的从 1 开始的稳定序号。
- `values` 来自 `DataRow.observed_values`；若旧数据没有该字段，再回退到 `DataRow.values`。
- 不发送用户已经确认后的值作为“原始观察值”。
- 不发送完整 `raw_text`、模型日志、图片 Base64 或修改记录，避免输出和上下文继续膨胀。
- 可选的 `experiment_context` 只能用于解释实验设计，不能授权模型改写数据。

### 4.2 可选输入

后续图片复核模式可额外接收：

- 原始 `SourceFile.content`；
- 目标行或区域的裁剪信息；
- 用户提供的实验设计说明；
- 已知变量允许值集合，例如第二变量只允许 `L/H`。

这些输入不属于 Step 1 最小版本。

## 5. 输出设计

### 5.1 推荐的顶层结构

建议 Validation 独立返回 `ValidationResult`，不要直接返回修改后的 `ExperimentResult`：

```json
{
  "warnings": [],
  "suggestions": [],
  "uncertain_items": [],
  "validation_metadata": {
    "provider": "doubao",
    "model": "configured-model",
    "status": "completed"
  }
}
```

三类结果的职责：

- `warnings`：全局或不能可靠绑定单元格的提醒，不直接提供修改操作。
- `suggestions`：已经定位到具体目标、存在候选值的可操作建议。
- `uncertain_items`：明确需要用户检查，但可能没有合理候选值的问题。

### 5.2 建议项结构

```json
{
  "finding_id": "validation-0001",
  "scope": "cell",
  "row_index": 5,
  "column_name": "treatment_id",
  "observed_value": "S0/AH/E+/N3",
  "issue_type": "identifier_pattern",
  "reason": "同一字段其他行的第二分段只出现 L 或 H，AH 可能包含多余字符。",
  "suggested_value": "S0/H/E+/N3",
  "confidence": "low"
}
```

字段约束：

| 字段 | 含义 | 约束 |
|---|---|---|
| `finding_id` | 本次校验内唯一标识 | 用于页面状态和审计，不依赖文本去重 |
| `scope` | 问题范围 | `cell`、`column`、`row` 或 `global` |
| `row_index` | 页面稳定行号 | 单元格/行问题必填；其他范围可为 `null` |
| `column_name` | 字段内部名 | 单元格/字段问题必填 |
| `observed_value` | Extraction 原始观察值 | 只读，必须与输入快照一致 |
| `issue_type` | 问题类别 | 使用受控枚举 |
| `reason` | 简短中文依据 | 不应包含长篇推理过程 |
| `suggested_value` | AI 候选值 | 没有合理候选时必须为 `null` |
| `confidence` | 建议可信程度 | `low`、`medium`、`high`，仅供参考 |

建议的 `issue_type` 最小枚举：

- `missing_value`
- `type_mismatch`
- `identifier_pattern`
- `unit_inconsistency`
- `replicate_inconsistency`
- `numeric_format`
- `possible_outlier`
- `unresolved_character`
- `other`

### 5.3 不确定项结构

`uncertain_items` 与建议项使用相同定位字段，但允许 `suggested_value=null`：

```json
{
  "finding_id": "validation-0002",
  "scope": "cell",
  "row_index": 8,
  "column_name": "measurement",
  "observed_value": "0.0?",
  "issue_type": "unresolved_character",
  "reason": "数值包含无法确认的字符。",
  "suggested_value": null,
  "confidence": "low"
}
```

同一问题出现在多行时，每个行列位置都应有独立 `finding_id`，不能合并成一条无法操作的描述。

### 5.4 警告结构

最小版本可使用字符串列表；后续若需要严重程度，可升级为：

```json
{
  "code": "possible_missing_rows",
  "severity": "warning",
  "message": "编号序列存在间断，请对照原图检查。"
}
```

警告不能自动创建缺失行，也不能据此改变最终数据。

## 6. 与现有数据结构的兼容性

### 6.1 当前 `ExperimentResult` 可以复用的内容

当前结构已有：

- `rows` 和 `DataRow.observed_values`：保存原始观察与当前值；
- `ai_suggested_rows`：可以暂时保存按行组织的 AI 建议；
- `uncertain_items`：可以显示基础不确定信息；
- `warnings`：可以保存全局提醒；
- `modification_records` 和 `field_sources`：可以追踪用户确认来源；
- `model_response_logs`：可以在开发模式保存 Validation 原始响应和诊断。

因此，最小验证可以在不改变 Extraction 行的前提下运行。

### 6.2 当前结构的不足

当前 `UncertainItem` 只有：

- `location`
- `content`
- `reason`

它缺少稳定的 `row_index`、`column_name`、`observed_value`、`suggested_value`、`issue_type` 和 `confidence`。如果继续把这些内容编码进字符串，页面需要反复解析自然语言位置，容易出现“无法自动定位”。

### 6.3 推荐的数据模型演进

v0.2.2 Step 1 建议新增独立的结构化对象，而不是修改 `DataRow`：

```text
ValidationFinding
ValidationResult
```

然后给 `ExperimentResult` 增加一个默认值为空的可选字段：

```text
validation_result: ValidationResult | None = None
```

这样可以：

- 保持旧结果和 Mock 流程兼容；
- 避免 Validation 直接改写 Extraction 数据；
- 让页面可靠定位具体单元格；
- 将用户对建议的决定单独记录；
- 在 Validation 失败时保留完整 Extraction 结果。

如果 Step 1 必须完全不改数据模型，也可以临时把结果映射进现有 `warnings`、`uncertain_items` 和 `ai_suggested_rows`，但这只适合作为短期验证，不建议成为长期结构。

## 7. Provider 与调用流程设计

### 7.1 是否扩展现有 `VisionProvider`

当前 `VisionProvider.process_images(images, experiment_context)` 的职责是“图片 → ExperimentResult”。Validation 的主要输入是 `ExperimentResult`，并不天然需要图片。因此不建议直接修改这个抽象方法或把结构化 JSON 塞进 `experiment_context`。

推荐保持现有 `VisionProvider` 不变，新增独立能力接口：

```text
ValidationProvider.validate_result(
    experiment_result,
    experiment_context=None,
    source_images=None,
) -> ValidationResult
```

同一个具体 Provider（例如 `DoubaoProvider`）未来可以同时实现 VisionProvider 和 ValidationProvider。这样新增 OpenAI、Claude 或 Gemini 实现时，Extraction 和 Validation 都遵守统一约定，但旧 Provider 不会被强制破坏。

### 7.2 `stage="validation"` 的建议方式

当前 `DoubaoProvider.process_images(..., stage="extraction")` 中的 `stage` 是具体实现的关键字参数，并未出现在抽象 `VisionProvider` 中。

不建议增加 `process_images(stage="validation")`，原因是它仍然只能接收图片，无法清楚表达 Validation 的结构化输入。

建议把阶段名称放在编排层：

```text
core/validation_service.py
    validate_experiment_result(...)

providers/base_validation_provider.py
    ValidationProvider

providers/doubao_provider.py
    validate_result(...)
```

如果未来确实需要统一 `stage` 调用，可再设计通用的 `run_stage(stage, payload)` 接口，其中：

- `stage="extraction"` 的 payload 是图片；
- `stage="validation"` 的 payload 是只读 ExperimentResult 快照；

但这属于更大范围的接口重构，不应作为 v0.2.2 Step 1 的前置条件。

### 7.3 新 Prompt 文件

建议新增：

```text
prompts/validation_prompt.py
```

职责：

- 接收精简的观察数据 JSON；
- 只返回 `warnings`、`suggestions` 和 `uncertain_items`；
- 不返回完整 `observed_rows`；
- 不重写 Extraction 结果；
- 限制原因文字长度；
- 要求严格 JSON，不输出 Markdown；
- 每个可操作问题必须包含明确 `row_index` 和 `column_name`。

现有 `scientific_data_validation_prompt.py` 可以保留为 legacy 校验 Prompt，避免直接覆盖已经验证过的旧流程。

## 8. 推荐运行流程

```text
图片
  ↓
Extraction Provider
  ↓
ExperimentResult（观察数据，保持不变）
  ↓
构造只读 Validation 输入快照
  ↓
Validation Provider
  ↓
ValidationResult
  ├─ warnings
  ├─ suggestions
  └─ uncertain_items
  ↓
用户接受 / 拒绝 / 手动修改
  ↓
final_value + 来源记录
  ↓
Excel
```

失败隔离：

```text
Validation 超时、API 错误或 JSON 解析失败
  ↓
显示“AI 数据检查未完成”
  ↓
保留 Extraction 数据
  ↓
允许用户继续人工检查和导出
```

## 9. 人工确认页面影响

### 9.1 页面层级

未来页面仍应以完整结构化表格为中心：

1. 显示 Extraction 得到的当前整理结果；
2. 对 Validation 定位成功的单元格增加提示标记；
3. 在对应确认区域显示问题类型、原始值、AI 建议和简短原因；
4. 全局 warnings 放在独立折叠区域；
5. 无法定位的问题保留为人工检查提醒，不阻塞其他数据。

### 9.2 用户操作

对存在 `suggested_value` 的项目提供：

- **接受 AI 建议**：把建议写入最终值，来源记录为 `ai_suggestion_accepted`；
- **拒绝建议 / 保留原始**：最终值保持观察值，来源记录为 `user_kept_original`；
- **手动修改**：使用用户输入值，来源记录为 `user_modified`。

对没有建议值的项目提供：

- **确认原始值**；
- **手动修改**。

建议状态应独立保存为：

```text
pending
accepted
rejected
manually_resolved
```

用户点击前，`suggested_value` 不能进入最终数据。

### 9.3 不应发生的行为

- Validation 返回后自动刷新或覆盖表格单元格；
- 因置信度为 high 自动采用建议；
- 因异常提示删除一行；
- 因无法定位而让整个页面崩溃；
- 把全局警告伪装成具体单元格错误。

## 10. Excel 三个工作表的影响

v0.2.2 应继续保留现有三个工作表，不需要为最小版本新增工作表。

### 10.1 整理后数据

- 只导出用户最终确认后的 `final_value`；
- 未接受的 AI 建议不能进入该表；
- Validation 失败不应阻止导出 Extraction/人工确认结果；
- 保持当前连续序号和有效行规则。

### 10.2 字段说明

- 保留原始字段名和单位；
- 字段级建议单独记录为 AI 建议；
- 用户确认后记录最终字段名或单位及其来源；
- 未确认的建议不能冒充最终字段信息。

### 10.3 识别记录

建议在现有识别记录中保留：

- Extraction 原始观察数据摘要；
- Validation 的 warnings、suggestions 和 uncertain_items；
- 每条建议的 `finding_id`、行号、字段、观察值、建议值、原因和置信度；
- 用户对建议的接受、拒绝或手动修改决定；
- Provider、模型、运行状态、响应 ID 和时间；
- Validation 失败或超时信息。

识别记录是审计信息，不应反向覆盖“整理后数据”。

## 11. 错误处理与稳定性

Validation 应复用 v0.2.1 已验证的稳定性原则：

- 单次 API 调用有明确超时；
- 区分网络错误、API 错误、超时、JSON 解析错误和输出截断；
- 记录响应 ID、`finish_reason`、token usage、输出长度和 API 耗时，不记录 API Key；
- JSON 无效时最多进行一次受控重试；
- 重试提示只要求返回完整、精简 JSON；
- Validation 失败不回滚或清空 Extraction 结果。

为控制输出长度，Validation 不应返回完整观察数据副本，也不应输出长篇推理过程。

## 12. 测试策略

### 12.1 不调用真实 API 的测试

- 输入 `ExperimentResult` 后生成稳定的只读 JSON 快照；
- `observed_values` 不被 Validation 修改；
- 建议项能按 `row_index + column_name` 定位；
- 无法定位的项目转为 warning，不抛出页面级异常；
- 接受、拒绝和手动修改分别记录正确来源；
- Validation 超时后仍可使用 Extraction 结果；
- 旧 Mock、legacy 和 Excel 流程保持兼容。

### 12.2 真实 API 小样本测试

建议先选 3 类图片：

1. 普通清晰表格；
2. 含模糊编号和缺失单位的图片；
3. 含重复实验和可疑数值的图片。

记录：

- Validation JSON 成功率；
- 平均耗时和输出长度；
- 可定位建议比例；
- 人工判断的有效建议比例；
- 错误建议数量；
- 是否出现任何原始数据被修改。

### 12.3 人工标注

Validation 的质量不能只用“JSON 是否成功”衡量。需要为小样本建立人工真值，分别统计：

- 真异常被发现的比例；
- 正常数据被误报的比例；
- 建议值正确率；
- 无建议但正确提示人工检查的比例。

在样本不足前，不应宣传自动异常检测准确率。

## 13. 开发顺序建议

### Step 1：Validation 最小版本

目标：验证独立的数据检查链路，不改 UI 主流程。

建议工作：

1. 定义 `ValidationFinding` 和 `ValidationResult` 的最小结构；
2. 新建精简 `validation_prompt.py`；
3. 新建 `ValidationProvider` 能力或等价的独立调用方法；
4. 新建平台无关的 `validate_experiment_result()`；
5. 使用 Mock 验证输入只读、定位字段、异常分类和失败隔离；
6. 用少量真实图片测试输出长度与 JSON 稳定性。

验收标准：

- Validation 不修改任何 Extraction 行；
- 返回结果可稳定绑定行列；
- 失败时 Extraction 结果保持可用；
- 不输出完整观察数据副本；
- 不实现自动接受建议。

### Step 2：人工确认增强

目标：把 Validation 建议安全接入现有确认页面。

建议工作：

1. 在表格中标记有 Validation finding 的单元格；
2. 增加接受、拒绝和手动修改操作；
3. 记录决定状态和最终值来源；
4. 把 Validation 审计信息写入现有“识别记录”工作表；
5. 完整测试确认后 Excel 只使用最终值。

验收标准：

- AI 建议永远不会自动覆盖；
- 每次操作都能追溯；
- 定位失败不会影响其他行；
- Excel 主数据与页面最终确认值一致。

### Step 3：高级异常检测

目标：在人工标注和最小版本稳定后，逐步扩展科研检查能力。

可选方向：

- 重复实验数量与编号一致性；
- 变量组合和处理编号规律；
- 字段级单位一致性；
- 基于用户指定规则的数值范围检查；
- 可解释的统计异常提示。

该步骤不应默认执行平均值、标准差、方差分析或自动删除异常值。统计检查必须区分“计算结果”和“实验事实”，并由用户决定是否采用。

## 14. 推荐的 v0.2.2 最小范围

为了保持个人开发者可控的 MVP 范围，v0.2.2 建议只交付：

- 独立 Validation Prompt；
- 结构化 ValidationResult；
- 数据只读校验服务；
- Mock 测试和 3 张真实图片验证；
- Validation 失败隔离；
- 最基础的人工接受/拒绝流程。

暂缓：

- 自动统计分析；
- 多模型交叉验证；
- 多轮 Agent 推理；
- 自动单位推断和换算；
- 自动删除、填补或修正实验数据；
- 大规模数据库和用户系统。

## 15. 结论

当前 `ExperimentResult` 已包含原始观察、建议、警告和来源追踪的基础能力，因此 v0.2.2 可以在不推翻 v0.2.1 的前提下增加 Validation。

最关键的架构选择是：把 Validation 设计为独立、只读、可失败的第二阶段，而不是重新生成完整数据或复用图片提取接口改写结果。最小版本应优先解决结构化定位、失败隔离和用户授权问题，再逐步增加高级科研异常检测。
