## 3. Provider 选择

现有 `providers/validation_provider_factory.py` 已支持：

```text
mock   → MockValidationProvider
doubao → DoubaoValidationProvider
```

因此本次不需要修改 Provider 工厂，只需要让 UI 调用时传入正确名称。

普通页面：

```text
provider_name="doubao"
```

开发模式：

```text
provider_name="mock"
```

普通用户仍不需要选择模型或 Provider。

## 4. 状态与失败隔离

Validation 继续使用独立 Session State：

```text
validation_status_{result_id}
validation_result_{result_id}
validation_error_{result_id}
```

真实 API 失败时：

- 状态切换为 `failed`；
- 保存可读错误信息；
- 不保存无效 ValidationResult；
- 不删除或修改 Extraction 结果；
- 页面仍可继续查看、编辑和导出 Extraction 数据；
- 用户可以主动重新运行 Validation。

## 7. 真实结果分析

真实 Provider 调用链已经成功，证明以下流程可运行：

```text
Extraction ExperimentResult
→ 精简 Validation Prompt
→ Doubao API
→ 严格 JSON
→ ValidationResult
```

但结果质量仍需继续验证：

- 12 行数据产生 24 条 warnings，数量偏多；
- 没有形成可直接采用的 suggestions；
- 只有 1 条通过结构化行列绑定的不确定项；
- 输出长度 7429 字符，仍然不算短。

这些结果说明“真实 API 接通”不等于“Validation 建议质量成熟”。可能原因包括：

- 模型返回了无法绑定当前字段名或行号的 finding，被服务降级为 warning；
- Prompt 对问题覆盖较广，模型产生了过多提醒；
- 单张样本不足以判断 suggestions 缺失是 Prompt、数据本身还是模型随机性造成。

本步骤不为改善结果而继续修改 Prompt，也不自动采用任何建议。

## 9. 当前限制

- Validation 建议仍为只读展示，尚未接入接受、拒绝和手动修改；
- findings 尚未在主数据表中高亮；
- Validation 审计信息尚未写入 Excel；
- 只完成 1 张真实图片测试，不能代表总体准确率；
- 当前 warnings 数量偏多，需要先分析原始 Validation finding 的定位质量；
- Validation 会产生额外 API 费用和约几十秒等待时间。

## 10. 下一步建议

在进入建议确认前，建议先完成 3 份脱敏 Extraction 结果的小样本评估：

1. 记录原始 suggestions 和 uncertain_items 数量；
2. 统计有效行列定位比例；
3. 人工判断 warning 是否真实有用；
4. 检查 suggestions 为 0 的原因；
5. 控制输出长度，避免 Validation 再次出现 JSON 截断风险。

确认结构化 finding 的质量后，再进入 Validation Step 2.3：表格定位、高亮和用户接受/拒绝流程。
