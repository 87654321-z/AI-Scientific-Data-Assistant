# v0.2.2 Validation Step 2 UI 集成方案

## 1. 目标与边界

Step 2 的目标是把已经完成的独立 Validation 基础流程接入 Streamlit，让用户在 Extraction 成功后主动运行 AI 数据检查，并对每条结构化建议执行接受、拒绝或手动修改。

本方案坚持：

1. Extraction 仍然是唯一的图片结构化提取阶段；
2. Validation 只读取 Extraction 观察数据；
3. ValidationResult 与 ExperimentResult 分开保存；
4. Validation 失败不能清空或覆盖 Extraction 结果；
5. AI 建议只有经过用户操作才能影响最终数据；
6. 第一步 UI 集成不改变 Excel 结构，也不自动调用 Validation；
7. 普通用户不需要选择 Provider 或模型名称。

本文件只描述方案，不修改代码。

## 2. 当前 Streamlit 页面流程

当前主页面是：

```text
pages/2_OCR.py
```

### 2.1 图片和 Extraction

当前流程：

```text
上传单张图片
  ↓
读取并显示原图
  ↓
可选：启用大图四栏预处理
  ↓
点击“开始 AI 科研数据整理”
  ↓
process_experiment_images(..., provider_name="doubao")
  ↓
ExperimentResult 保存到 st.session_state[doubao_key]
  ↓
render_ai_result(...)
```

`doubao_key` 当前按图片标识保存 Extraction 结果：

```text
doubao_result_{image_id}
```

新图片上传后，页面清理部分 OCR 和确认状态；Extraction 成功后也会清理旧确认值、确认记录和表格编辑器状态。

### 2.2 当前结果展示

`render_ai_result()` 当前负责：

- 初始化确认值、确认记录、来源和忽略行状态；
- 解析旧 `ExperimentResult.uncertain_items`；
- 绑定具体行列；
- 计算确认进度；
- 构造中文数据表和连续序号；
- 黄色高亮未确认单元格；
- 展示原始识别文本和开发日志；
- 展示不确定项及操作按钮；
- 提供数据表编辑和“是否纳入最终结果”；
- 调用 `confirm_experiment_result()`；
- 调用 `export_experiment_result_to_excel()`；
- 生成 Excel 下载按钮。

### 2.3 当前人工确认状态

主要 Session State：

```text
doubao_confirmed_values_{image_id}
doubao_confirmation_records_{image_id}
doubao_confirmation_sources_{image_id}
doubao_ignored_row_indices_{image_id}
doubao_uncertain_bindings_{image_id}
doubao_selected_cell_{image_id}
doubao_editor_{image_id}
doubao_excel_{image_id}
```

当前单元格最终值使用：

```text
"{source_row_index}:{column_name}"
```

其中 `source_row_index` 是从 0 开始的内部索引。

### 2.4 当前流程需要注意的问题

1. 旧不确定项依赖 `parse_uncertain_item()` 从字符串解析结构化字段；ValidationFinding 已是结构化对象，不应再次转换成字符串。
2. ValidationFinding 的 `row_index` 从 1 开始，而当前页面确认键使用从 0 开始索引，必须在单一适配层转换。
3. 页面已有确认数据来源逻辑，Validation 不应另建第二份最终表。
4. 页面当前即使存在未确认项也可以生成 Excel；Step 2 不宜突然改变这一行为。
5. Extraction 结果保存在 Session State，Validation 必须与具体 Extraction 运行绑定，不能复用上一张图或上一轮提取结果。

## 3. Validation 调用位置

### 3.1 推荐位置

Validation 应在 Extraction 已成功且 `doubao_key` 已存在之后提供入口：

```text
if doubao_key in st.session_state:
    显示 Extraction 结构化结果
    显示“运行 AI 数据检查”按钮
    如果已有 ValidationResult：显示检查结果
    继续显示人工编辑和 Excel 导出
```

逻辑调用：

```python
validate_experiment_result(
    st.session_state[doubao_key],
    provider_name="doubao",
)
```

### 3.2 MVP 使用显式按钮

建议按钮名称：

```text
运行 AI 数据检查
```

不要在 Extraction 完成后自动调用，原因：

- Validation 会产生第二次 API 调用和费用；
- 用户可能只需要快速提取和手动检查；
- Validation 失败不应被误解为 Extraction 失败；
- 显式按钮便于分别记录 Extraction 与 Validation 耗时；
- 当前尚未完成大规模 Validation benchmark。

按钮下方应提示：

```text
AI 数据检查会再次调用模型，可能产生额外费用和等待时间。检查结果仅供参考，不会自动修改数据。
```

### 3.3 Provider 选择

普通用户不显示 Provider 下拉框。

- 正式页面使用与 Extraction 相同的后台配置，调用 `provider_name="doubao"`；
- `MockValidationProvider` 只在 `developer=true` 时提供开发测试入口；
- 未来更换模型仍由 Provider 工厂和后台配置负责。

### 3.4 调用状态

建议使用独立状态机：

```text
not_started  尚未运行
running      正在检查
completed    检查完成
failed       检查失败
stale        Extraction 已重新运行，旧校验失效
```

页面显示：

- 未运行：“尚未运行 AI 数据检查”；
- 运行中：`st.spinner("AI 正在检查结构化数据，请稍候……")`；
- 成功：“AI 数据检查完成，请人工确认提示项”；
- 失败：“结构化数据提取成功，但 AI 数据检查未完成”；
- 失效：“数据已重新提取，请重新运行 AI 数据检查”。

### 3.5 Session State 设计

建议新增：

```text
validation_result_{result_id}
validation_status_{result_id}
validation_error_{result_id}
validation_decisions_{result_id}
validation_timings_{result_id}
```

`result_id` 不应只使用文件名。建议由以下内容生成稳定指纹：

```text
图片内容哈希
+ Extraction 结果行列摘要哈希
+ Extraction 运行标识
```

最小实现也可以使用：

```text
image_id + extraction_run_id
```

Extraction 每次重新运行时：

- 生成新的 `extraction_run_id`；
- 清除对应 ValidationResult、错误、决定和下载缓存；
- 不让旧建议作用到新数据。

## 4. 页面展示方案

### 4.1 页面信息顺序

建议保持“数据表优先”：

```text
1. 原始图片
2. Extraction 当前整理结果表
3. AI 数据检查入口与状态
4. Validation 摘要
5. 需要确认的单元格
6. 全局提醒
7. 数据表编辑
8. Excel 导出
```

不建议先展示长建议卡片，再让用户寻找表格位置。

### 4.2 Validation 摘要

检查完成后显示四个指标：

```text
检查状态
可操作建议数
仅需人工检查数
全局提醒数
```

再显示确认进度：

```text
已处理建议 / 全部可处理项
```

其中：

- `suggestions` 是存在候选值的项目；
- `uncertain_items` 可能没有候选，但仍需确认原始值或手动修改；
- `warnings` 不计入必须逐项确认的进度。

### 4.3 表格高亮

ValidationFinding 已包含 `row_index` 和 `column_name`，页面应直接定位，不使用自然语言解析。

适配规则：

```text
Validation row_index（1开始）
    ↓ 减1
source_row_index（0开始）
    ↓
当前页面 value_key = "source_row_index:column_name"
```

高亮建议：

- 未处理 Validation 项：浅黄色；
- 当前用户定位的单元格：深黄色；
- 已处理项：取消黄色；
- 全局 warning：不高亮单元格；
- 无效定位已由 `validation_service` 降级为 warning。

页面序号仍使用 `build_display_dataframe()` 生成的连续“序号”。提示文案同时显示：

```text
序号 5（原始第 7 行）· 处理编号
```

这样即使某些行被忽略，用户仍能区分当前显示序号和原始行位置。

### 4.4 Finding 展示

每个单元格项目默认只显示：

```text
位置
原始观察值
AI 建议值
当前最终值
操作按钮
```

辅助信息放入折叠区域：

```text
问题类型
简短原因
置信度
finding_id（仅开发模式显示）
```

用户可见问题类型应中文化：

| 内部 issue_type | 页面显示 |
|---|---|
| `missing_value` | 缺失值 |
| `type_mismatch` | 数据类型不一致 |
| `identifier_pattern` | 实验编号格式可疑 |
| `unit_inconsistency` | 单位不一致 |
| `replicate_inconsistency` | 重复实验信息不一致 |
| `numeric_format` | 数字格式可疑 |
| `possible_outlier` | 数值可能异常 |
| `unresolved_character` | 字符无法确认 |
| `other` | 其他需检查问题 |

置信度显示：

```text
high   → 高
medium → 中
low    → 低
```

但页面应继续提示：高置信度也不会自动修改数据。

### 4.5 多个 Finding 指向同一单元格

Validation 可能对同一单元格同时报告编号格式和模糊字符问题。

MVP 建议按单元格分组：

- 表格只高亮一次；
- 卡片内列出全部问题原因；
- 如果建议值相同，只显示一次建议和一组操作；
- 如果建议值冲突，不允许一键采用，提示用户手动修改；
- 每个 finding 的决定仍分别记录，便于追溯。

禁止后一条 finding 静默覆盖前一条建议。

### 4.6 全局提醒

`warnings` 放在：

```text
查看 AI 数据检查提醒
```

折叠区域中。

warning 只提供提醒，不显示“采用建议”按钮，也不阻止页面其他操作。

## 5. 用户确认流程

### 5.1 三种操作

对有 `suggested_value` 的项目：

#### 采用 AI 建议

```text
final_value = suggested_value
decision = accepted
source = ai_suggestion_accepted
```

#### 保留原始识别

```text
final_value = observed_value
decision = rejected
source = user_kept_original
```

#### 手动修改

```text
final_value = 用户输入
decision = manually_resolved
source = user_modified
```

对没有 `suggested_value` 的 uncertain item：

- 不显示可用的“采用 AI 建议”；
- 提供“确认原始值”和“手动修改”；
- 允许用户明确确认空值。

### 5.2 与现有确认值合并

Validation 不创建第二份最终数据表。

用户操作仍写入现有：

```text
doubao_confirmed_values_{image_id}
doubao_confirmation_sources_{image_id}
doubao_confirmation_records_{image_id}
```

单元格键继续使用：

```text
"{source_row_index}:{column_name}"
```

Validation 另外保存审计决定：

```text
validation_decisions_{result_id}[finding_id] = {
    "decision": "accepted | rejected | manually_resolved",
    "observed_value": ...,
    "suggested_value": ...,
    "confirmed_value": ...,
    "source": ...
}
```

这样：

- 现有数据表和 Excel 的最终值来源保持统一；
- Validation 的每条建议仍可独立追溯；
- 不需要修改 Extraction 结果。

### 5.3 结构化编号安全提醒

继续复用现有科研编号保护逻辑：

- 页面显示可以使用上下标格式；
- 内部保存使用普通字符串；
- AI 建议改变分段结构时显示安全提醒；
- 用户仍可明确接受，但系统不能自动采用；
- `observed_value` 永远不改变。

### 5.4 数字和空值

- 数字最终值继续使用当前数值规范化逻辑；
- AI 建议中的小数逗号只在写入最终值时执行现有规范化；
- `observed_value` 保持原样；
- 用户可以确认空字符串或 `None`；
- 单字段为空不代表整行无效。

### 5.5 确认进度

建议把两类进度分开：

```text
Extraction 待确认项：x / y
Validation 检查项：a / b
```

不要把 warning 计入确认项，也不要用 Validation 覆盖旧不确定项数量。

当两者都处理完成时显示：

```text
所有待确认项目已处理。
```

### 5.6 是否阻止 Excel 导出

Step 2 不建议硬性阻止导出，因为：

- 当前流程允许用户自行决定何时导出；
- Validation 可能失败或用户选择不运行；
- 原始观察值必须始终可人工导出；
- 硬阻止会让 Validation 变成单点故障。

存在未处理建议时，在“生成 Excel”按钮附近显示：

```text
仍有 N 个 AI 数据检查项目未处理；若继续导出，将保留当前最终值。
```

用户仍可导出，但不能误以为所有建议都已确认。

## 6. 建议的页面适配结构

为避免继续扩大 `pages/2_OCR.py`，Step 2 建议新增轻量 UI 辅助模块：

```text
ui/
    validation_ui.py
```

或者在现有项目不希望新增顶层目录时使用：

```text
utils/
    validation_ui.py
```

建议函数：

```text
render_validation_controls(...)
build_validation_cell_groups(...)
apply_validation_decision(...)
render_validation_summary(...)
```

页面只负责：

- 传入 ExperimentResult 和 image/result id；
- 调用独立 Validation service；
- 把确认回调连接到现有 confirmed_values；
- 展示结果。

不要把 Validation 数据处理、API 调用和 Streamlit 控件再次混写在一个大函数中。

## 7. 错误处理

Validation 异常必须与 Extraction 异常分开。

### 7.1 页面文案

```text
Extraction 失败：
AI 科研数据整理失败，请查看错误信息。

Validation 失败：
结构化数据已成功生成，但 AI 数据检查未完成。
```

详细错误仍放在折叠区域：

```text
查看 AI 数据检查详细错误
```

### 7.2 失败后的行为

Validation 失败后：

- 保留 Extraction 数据表；
- 保留用户已经完成的人工修改；
- 允许重新运行 Validation；
- 允许继续生成 Excel；
- 不清空旧图片或重新调用 Extraction；
- 不把 Validation 错误包装成“图片损坏”。

### 7.3 重试

Provider 内部已有 JSON 最多一次重试。页面不应再自动循环重试。

页面只提供用户主动点击：

```text
重新运行 AI 数据检查
```

并提示这会产生新的 API 调用。

## 8. 耗时与费用提示

Validation 使用独立计时：

```text
validation_api_seconds
validation_total_seconds
validation_attempts
```

不要把 Validation 耗时合并进 Extraction 的 `api_call_seconds`。

开发模式可以显示：

- response id；
- finish_reason；
- token usage；
- output_length；
- attempts 数量。

普通用户只显示总耗时和是否发生重试，不显示 API Key、完整配置或内部异常对象。

## 9. Excel 未来兼容方案

### 9.1 Step 2 初期

最小 UI 集成阶段先不修改 Excel。用户接受 Validation 建议后，值写入现有 confirmed_values，最终仍通过：

```text
confirm_experiment_result()
→ export_experiment_result_to_excel()
```

因此“整理后数据”会自然使用用户确认后的值，不需要改变表结构。

不足是 Validation finding 和决定暂时不会完整写入 Excel 审计记录。页面应明确这是 Step 2 初期限制。

### 9.2 后续兼容设计

保持现有三个工作表：

#### 整理后数据

- 只输出最终确认值；
- 未接受的建议不进入主数据；
- 未处理建议保留当前值；
- Validation 不增加额外实验数据行。

#### 字段说明

- 字段级单位或名称建议单独记录；
- 用户接受后才成为最终字段信息；
- 字段来源记录为 AI 建议接受、用户保留或用户修改。

#### 识别记录

未来增加 Validation 审计内容：

- finding_id；
- 行号和字段名；
- observed_value；
- suggested_value；
- issue_type；
- reason；
- confidence；
- 用户 decision；
- confirmed_value；
- source；
- Provider 和响应诊断。

### 9.3 如何把 Validation 传给导出层

当前 `ExperimentResult` 没有 `validation_result`。有两种兼容方案：

#### 方案 A：给导出函数增加可选参数

```python
export_experiment_result_to_excel(
    experiment_result,
    output_path,
    validation_result=None,
    validation_decisions=None,
)
```

优点：不修改 ExperimentResult，符合 Step 1 的独立设计。

缺点：调用参数会增加，其他平台入口也要显式传递审计对象。

#### 方案 B：给 ExperimentResult 增加可选字段

```text
validation_result: ValidationResult | None = None
```

优点：统一结果对象更适合保存、导出和跨平台传递。

缺点：需要修改核心数据模型，并考虑序列化兼容。

### 9.4 推荐选择

Step 2 UI 初期使用方案 A，不修改 ExperimentResult；等 Validation 输出结构经过真实测试稳定后，再评估方案 B。

无论选择哪种方案，Excel 只能使用用户确认后的 final_value，不能直接使用 suggested_value。

## 10. 不影响 Extraction 的保证

### 10.1 不修改调用入口

保持：

```python
process_experiment_images(...)
```

签名、默认 Extraction stage 和返回值不变。

### 10.2 Validation 显式调用

只有用户点击“运行 AI 数据检查”时才调用：

```python
validate_experiment_result(...)
```

### 10.3 状态隔离

- Extraction 结果使用原 `doubao_key`；
- Validation 使用独立 key；
- Validation 失败不删除 `doubao_key`；
- 重新 Extraction 时使旧 Validation 状态失效；
- Validation 不能写 `doubao_result.rows`。

### 10.4 回归要求

每次 UI 集成测试必须确认：

- 不运行 Validation 时，页面行为与 v0.2.1 相同；
- Extraction API 只调用一次；
- EasyOCR 备用功能不受影响；
- 大图四栏预处理不受影响；
- 原不确定项确认仍可使用；
- 原 Excel 导出仍可使用；
- Validation timeout 后仍可编辑和导出 Extraction 结果。

## 11. Step 2 最小测试矩阵

### 11.1 Mock UI 测试

1. Extraction Mock 返回三行数据；
2. Validation Mock 返回一个模糊字符和一个缺失值；
3. 表格对应单元格黄色高亮；
4. 接受/保留/手动修改分别更新同一最终表；
5. 原 ExperimentResult 不变；
6. 页面 rerun 后决定仍保留。

### 11.2 状态失效测试

1. 对图片 A 完成 Validation；
2. 重新运行图片 A 的 Extraction；
3. 旧 ValidationResult 不再显示；
4. 上传图片 B；
5. 图片 A 的决定不能作用到图片 B。

### 11.3 错误测试

- 无 API Key；
- timeout；
- API 错误；
- JSON 两次失败；
- 无效行列定位；
- suggestions 为空；
- 多个 finding 指向同一单元格且建议冲突。

所有失败都必须保留 Extraction 表格和 Excel 按钮。

### 11.4 Excel兼容测试

Step 2 初期：

- 接受建议后主数据使用确认值；
- 拒绝建议后主数据保留 observed_value；
- 手动修改进入主数据；
- 未处理建议不自动进入主数据；
- 三个工作表结构不改变；
- Validation 失败仍可导出。

## 12. 建议实施顺序

### 小步骤 1：只显示 Mock Validation

- 新增 Validation UI 辅助模块；
- 页面增加显式按钮；
- 使用 MockValidationProvider；
- 展示摘要、warning 和结构化定位；
- 暂不允许操作建议。

验收：Extraction 页面完全不变，Mock 校验可独立成功或失败。

### 小步骤 2：接入确认操作

- 分组显示单元格 finding；
- 连接现有 confirmed_values；
- 支持接受、拒绝和手动修改；
- 保存 validation_decisions；
- 更新高亮和进度。

验收：用户操作立即更新最终表，但不修改 observed_value。

### 小步骤 3：启用 Doubao Validation

- 普通用户按钮调用 DoubaoValidationProvider；
- 增加费用和耗时提示；
- 显示失败隔离和重试入口；
- 使用脱敏 Extraction 结果做 1～3 份真实测试。

验收：真实 Validation 失败不影响 Extraction。

### 小步骤 4：Excel审计兼容

- 在不改变三个工作表数量的前提下，把 Validation finding 和用户决定写入“识别记录”；
- 验证主数据只使用最终确认值。

这一步应在 ValidationResult 字段经过真实测试稳定后进行。

## 13. Step 2 MVP 验收标准

- [ ] Extraction 函数、Prompt、Provider 和结果保持不变。
- [ ] Validation 只能由用户显式启动。
- [ ] 页面明确提示额外 API 调用和费用。
- [ ] Extraction 和 Validation 状态完全分离。
- [ ] ValidationFinding 使用结构化行列定位，不解析自然语言 location。
- [ ] 1 起始行号只在适配层转换一次。
- [ ] 表格优先展示，未处理单元格可高亮。
- [ ] 用户可以接受、拒绝或手动修改。
- [ ] AI 建议不能自动进入 final_value。
- [ ] 多个 finding 指向同一单元格时不会静默覆盖。
- [ ] Validation 失败时 Extraction、编辑和导出仍可使用。
- [ ] 不运行 Validation 时不增加 API 请求和耗时。
- [ ] Step 2 初期不修改 Excel 结构。

## 14. 结论

当前页面已有可复用的单元格确认、来源记录、高亮和 Excel 最终值流程。Validation Step 2 不应重新建立一套表格，而应把结构化 ValidationFinding 适配到现有 confirmed_values。

最安全的接入方式是：

```text
Extraction 表格保持不变
  ↓
用户显式运行 Validation
  ↓
ValidationResult 独立保存在 Session State
  ↓
结构化 finding 绑定现有单元格
  ↓
用户决定写入现有最终值与独立审计记录
```

建议先完成 Mock 展示和状态隔离，再接入确认操作，最后启用真实 Doubao Validation。这样可以控制 API 成本，避免 Validation 成为 Extraction 的单点故障，也为未来 Excel 审计保留清晰路径。
