# v0.2.2 Validation Quality Analysis

## 1. 分析目标与结论摘要

本报告分析真实 Doubao Validation 的结果质量，不评价 API 是否接通。Validation 的基本原则仍是：只检查 Extraction 结果，不修改原始实验数据，所有建议必须由用户确认。

核心结论：

1. 历史测试的 `24 warnings / 0 suggestions / 1 uncertain_item` 只能确认数量，24 条 warning 的原文没有保存，因此不能可靠地逐条还原和分类。
2. 使用同一张图片重新运行时，Extraction 仍得到 12 行，但 Validation 原始输出变为 `0 warnings / 0 suggestions / 1 uncertain_item`。同一输入差异很大，说明模型输出存在明显随机波动。
3. 当前服务会把无法绑定有效行列的 suggestion 或 uncertain item 删除，并转换成一句通用 warning。这是 warning 数量膨胀、suggestions 变为 0 的重要机制。
4. Prompt 的检查范围较宽，但没有 severity、总数上限和去重优先级，模型容易把“信息未提供”也当成数据错误。
5. 当前最优先的工作不是增加更多检查规则，而是保存原始 Validation 响应、提高字段绑定成功率，并控制高价值 finding 的数量。

## 2. 分析证据

### 2.1 历史真实测试

| 指标 | 历史结果 |

| Extraction 行数 | 12 |
| Validation warnings | 24 |

| Validation 输出长度 | 7429 字符 |

历史报告只保存了数量和性能指标，没有保存 24 条 warning 的原文、finding_id、行号、字段名和原因。因此，本报告不会虚构这 24 条内容。它们只能整体归入“尚无法人工判定”。

### 2.2 同图复测

同一图片重新 Extraction 后仍得到 12 行，字段为编号、处理名称、Na 含量和 K 含量。第 5 行处理名称包含 `[模糊字符]`，其余行均有完整的处理编号和测量值。

本轮 Validation 原始数量为：

| 类型 | 数量 |
|---|---:|
| warnings | 0 |
| suggestions | 0 |
| uncertain_items | 1 |

这与历史 `24 / 0 / 1` 明显不同。由于模型调用并未固定随机性参数，而且 Validation 本身是生成式判断，所以单次结果不具备稳定复现性。

### 2.3 受控结构化数据复测

为了检查字段绑定和标准化行为，另用同一批 12 行结构化数据执行了一次受控 Validation。原始模型输出为：

- 1 条 suggestion：第 5 行 `treatment_name` 包含模糊字符，但 `suggested_value` 实际为 `null`；
- 2 条 uncertain item：认为 `replicate_group` 和 `replicate_index` 未提供；
- 4 条 uncertain item：临时测试输入中的中文显示名因 Windows 管道编码变成问号后，被模型识别为未解析字符。

后两类中的编码问题是测试工具造成的，不代表正式页面数据。它仍揭示了一个重要事实：模型会把输入传输或显示层异常当作科研数据问题，Validation 无法自行区分数据错误与输入质量错误。

## 4. Warning 过多的原因

### 4.1 Prompt 问题

- 检查范围同时包含缺失、类型、编号、重复、单位、数值字符、模糊字符和上下文异常，覆盖面较广。
- 没有 severity，轻微格式问题与可能影响实验结论的问题处于同一层级。
- 没有总 finding 数量限制，也没有“同类问题合并还是逐行报告”的明确优先级。
- 对“字段未提供”和“字段值异常”的边界不够明确。例如 replicate 元数据为空可能是正常情况。
- Prompt 规定“无法绑定时写 warnings”，但 warnings 只是字符串，无法保留问题类型、来源和定位失败原因。
- suggestion 与 uncertain item 的语义约束不够强，模型可能把 `suggested_value=null` 的项目放入 suggestions。

### 4.2 输入信息不足

- Validation 只看到 Extraction 的结构化结果，看不到原图，无法判断模糊字符究竟是什么。
- 缺少实验设计说明，例如合法处理编号集合、合理数值范围、预期重复次数。
- 缺少字段语义和单位时，模型只能依赖通用科研常识，容易产生误报。
- 单张表格无法提供跨批次基线，异常值判断依据不足。

### 4.3 输出约束问题

- `warnings` 是字符串列表，缺少 finding_id、severity、issue_type、row_index 和 column_name。
- 没有强制每个 suggestion 必须包含非空 `suggested_value`。
- 没有要求模型按重要性排序，也没有限制例如“最多返回 10 条高价值 findings”。
- 未通过 JSON Schema 或枚举级结构约束保证行列绑定有效。

### 4.4 数据结构与后处理问题

- `ValidationFinding` 可以表达结构化问题，但 `warnings` 不能。
- `_normalize_findings()` 遇到无效绑定时会丢弃原 finding，只追加通用 warning，导致具体原因、原值和建议丢失。
- column scope 仍要求 column_name 必须是 Extraction 的正式字段；`replicate_group` 和 `replicate_index` 是行级元数据，不在 columns 中，因此相关 finding 必然被判定为无法绑定。
- 历史 Validation 原始响应未持久化，无法进行稳定性对比和人工质量标注。
- 当前没有去重键，例如 `(issue_type, row_index, column_name)`，相似提醒可能重复出现。

## 5. 下一步优化建议

### P0：先建立可评估性

1. 在开发测试中保存脱敏的原始 Validation JSON、标准化后结果和模型响应元数据。
2. 为固定的 3 至 5 份 Extraction 结果建立人工标注基准，标记每条 finding 是否有效。
3. 至少重复运行 3 次，统计 finding 的复现率，而不是只比较单次数量。

预计收益：能够准确区分 Prompt 问题、模型随机性和 Python 后处理问题。开发难度低。

### P1：Prompt 调整

1. 明确“未提供实验设计信息时，不检查该规则”，尤其是单位、重复次数和异常值范围。
2. 要求 suggestions 中的 `suggested_value` 必须非空；没有候选值时只能进入 uncertain_items。
3. 要求只报告会影响数据解释或导出的高价值问题。
4. 要求按 severity 排序并限制总量，例如最多 10 条；超过时只保留最高严重度，并在 summary 中报告省略数量。
5. 明确 replicate 元数据为空本身不是问题，只有存在重复证据且关系矛盾时才报告。

预计收益：显著减少无意义提醒，提高 suggestions 的可操作性。开发难度低到中等。

### P1：severity 设计

建议增加三级严重度：

- `high`：可能改变实验结论或导致错误样品对应，例如关键编号缺失、数值无法解析；
- `medium`：需要人工确认但数据仍可保留，例如模糊字符、重复索引冲突；
- `low`：格式、单位说明或非阻断性一致性问题。

页面默认展示 high 和 medium，low 折叠显示。severity 只决定展示优先级，不能授权 AI 修改数据。

### P1：finding 数量与去重

- 默认最多显示 10 条；建议 high 不限、medium 最多 6 条、low 最多 3 条。
- 使用 `(issue_type, row_index, column_name)` 去重。
- 全局问题只报告一次；单元格问题必须保留精确位置。
- 不应把定位失败的结构化 finding 变成只有一句话的 warning，应保留原内容并增加 `binding_status=unresolved`。

### P2：字段补充需求

建议后续输入增加可选、由用户提供的上下文，而不是让 AI 猜测：

- 合法处理编号模式或示例；
- 字段数据类型；
- 单位及允许为空规则；
- 合理数值范围；
- 预期重复次数；
- 样品总数或预期行数；
- 哪些字段是关键字段。

这些字段应是可选配置。没有配置时，Validation 应降低判断强度并明确“证据不足”。

## 6. 推荐的最小下一步

下一步建议只做一次小改进：建立固定 Validation 质量样本集，并让原始 finding 在标准化失败时仍可追踪。随后再调整 Prompt：加入 severity、非空 suggested_value 规则、最多 10 条高价值 findings，以及 replicate 空值不自动报警规则。

在完成上述评估前，不建议直接把 Validation 建议接入自动修改或 Excel 主数据表。
