## 4. README 需要更新的内容

当前 README 仍写着：

```text
阶段2 Validation 目前仍是设计目标，尚未正式接入默认流程。
```

这已经与当前代码不一致，发布前必须更新。

### 4.1 版本与项目状态

建议把顶部版本从 `v0.2.1.2` 更新为 `v0.2.2.3`，并明确：

- Extraction 是第一阶段；
- Validation 是用户主动运行的第二阶段；
- Validation 已支持 Mock 和真实 Doubao Provider；
- Validation 失败不会影响 Extraction 数据、人工确认或 Excel；
- AI 检查仍需人工判断，不能自动修改实验数据。

### 4.2 当前支持功能

建议新增：

- 对 Extraction 结构化数据运行独立 AI Validation；
- warnings、suggestions、uncertain_items 分离；
- ValidationRunLog 记录模型、耗时、成功状态和安全原始响应；
- finding 按 high、medium、low 分层；
- finding 去重、定位优先排序和数量限制；
- 原始 ValidationResult 与展示结果分离；
- Validation 失败降级，不破坏主流程。

避免写成：

- “自动发现所有科研错误”；
- “保证异常检测准确”；
- “AI 自动修复数据”。

### 4.3 使用说明

在现有步骤“AI Extraction 完成”之后增加：

1. 查看结构化观察数据；
2. 点击“运行 AI 数据检查”；
3. 查看高、中、低风险 findings；
4. 对 AI 建议进行人工判断；
5. 即使 Validation 失败，也可以继续原有确认和 Excel 流程。

应提醒用户：Validation 会增加一次模型 API 调用，产生额外等待时间和可能的调用费用。

### 4.4 当前限制

建议补充：

- Validation 只检查 Extraction 结果，不重新查看原图；
- findings 存在随机波动，同一输入多次运行可能不同；
- severity 和 confidence 只用于排序与辅助判断；
- Quality Filter 减少重复提醒，但不证明剩余 finding 一定正确；
- 行列定位目前仍是基础能力，部分 finding 可能显示“尚未验证”或“无法定位”；
- Validation 日志当前在运行内存中，不是长期审计数据库；
- Validation 建议尚未自动写入 Excel 或 final_value。

## 5. Extraction–Validation 架构展示方案

README 建议使用下面的主流程，而不是把 Validation 写成 Extraction 的内部步骤：

```text
实验记录图片
      ↓
阶段1 Extraction
提取 columns、observed_rows、重复关系
      ↓
ExperimentResult（原始观察数据）
      ├───────────────────────────┐
      ↓                           ↓
人工确认主流程             阶段2 Validation（可选）
      │                    只检查结构化数据
      │                           ↓
      │              warnings / suggestions /
      │                   uncertain_items
      │                           ↓
      │                   Quality Filter
      │              去重 / 分级 / 排序 / 限量
      │                           ↓
      └──────────── 用户人工判断 ─┘
                  ↓
             最终确认数据
                  ↓
                Excel
```

需要突出三个边界：

1. Validation 不修改 ExperimentResult；
2. Validation 是可选步骤，失败不阻断主流程；
3. Quality Filter 只优化展示，不删除原始 finding。

目录职责可以补充：

```text
core/validation_service.py       Validation 编排与 Extraction 只读保护
core/validation_schemas.py       独立 ValidationResult 与运行日志
core/validation_quality.py       finding 去重、排序和数量限制
providers/*validation*           Mock 与真实 Validation Provider
prompts/validation_prompt.py     只检查结构化数据的 Prompt
utils/validation_ui.py           独立状态与分级展示
```

## 6. 项目成长过程的描述方式

建议把开发历程写成“发现问题—测量问题—拆分架构—增加可靠性”的工程故事。

### 阶段一：完成 MVP 闭环

```text
图片 → AI → 表格 → 人工确认 → Excel
```

先证明用户流程可运行，而不是一开始构建复杂平台。

### 阶段二：真实 benchmark 暴露输出截断

10 张真实图片测试发现长 JSON 会被截断，API 占主要耗时。项目没有盲目增加重试，而是记录 finish_reason、token、输出长度和耗时。

### 阶段三：v0.2.1 拆出 Extraction

首轮只输出结构化观察数据，减少响应长度并保留 legacy 回退。这体现了通过实验数据调整架构，而不是只调整 Prompt。

### 阶段四：v0.2.2 增加独立 Validation

Validation 只接收 Extraction 结果，不重新识别图片，也不修改原始数据。Mock、真实 Provider、Session State 和失败降级均独立。

### 阶段五：v0.2.2.3 解决 Validation 自身可靠性

真实测试出现 24 条 warning、0 条 suggestion 和 finding 波动后，项目进一步增加：

- ValidationRunLog；
- 安全原始响应；
- severity、confidence、location_status；
- finding 去重、排序和数量限制；
- 原始结果与展示结果分离。

这个过程适合展示“从模型能调用”到“模型输出可观测、可降级、可审计”的工程思路。

## 7. 是否适合作为作品集展示

### 7.1 适合展示的部分

当前项目适合作为个人 AI 工程作品集，尤其适合高校导师和 AI / 数据科学实习面试官了解以下能力：

- 从真实科研痛点定义产品，而不是只做模型 Demo；
- 使用 Provider 接口隔离模型与业务逻辑；
- 用 benchmark 定位 JSON 截断和 API 长尾问题；
- 把生成式流程拆成 Extraction 与 Validation；
- 保留 observed、suggested、confirmed 的科研数据安全边界；
- 建立 timeout、错误分类、失败降级和安全日志；
- 用确定性本地规则处理模型随机输出；
- 通过单元测试保护 Extraction 不变性和密钥安全。

### 7.2 发布前仍需注意

项目可以作为“工程原型 / 研究型 MVP”展示，但不应描述成成熟科研生产系统：

- 当前真实测试样本量较小；
- 没有完整人工标注的准确率、召回率和误报率；
- Validation findings 存在随机波动；
- 行列定位仍需进一步验证；
- API 速度和费用由外部模型服务决定；
- 高密度手写数字识别仍是已知能力边界；
- 当前没有账户、数据库和长期审计存储。

### 7.3 推荐作品集展示重点

作品集首页建议突出三个可信成果：

1. **完整闭环**：真实图片到结构化数据、人工确认和 Excel；
2. **数据驱动迭代**：通过 benchmark 将单阶段 Prompt 改成 Extraction–Validation；
3. **可靠性工程**：日志、错误分类、只读边界、去重、分级、限量和失败降级。

不要把重点放在“用了豆包模型”，而应放在“模型可以替换，核心流程和可靠性规则独立于模型”。
