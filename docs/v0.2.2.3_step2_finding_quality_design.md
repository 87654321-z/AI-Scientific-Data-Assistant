# v0.2.2.3 Step 2 Finding Quality Optimization 设计

## 1. 目标与边界

Step 2 的目标是提高 Validation finding 的可用性：减少重复和低价值提醒，提高行列定位率，让用户优先看到真正需要处理的问题。

本步骤不改变以下原则：

- Extraction 结果是只读输入；
- Validation 独立运行、独立失败、独立保存；
- AI finding 只能提示，不能自动修改 observed_value 或最终实验数据；
- 被过滤、去重或隐藏的 finding 仍保留在 `ValidationRunLog` 或原始结果中；
- 同一输入的模型输出可能波动，不能把单次 finding 当作事实。

建议流程：

```text
ExtractionResult（只读）
        ↓
Validation Provider 原始 findings
        ↓
结构校验与定位
        ↓
质量分类、去重、排序、限量
        ↓
主列表 + 折叠列表 + 原始日志
        ↓
用户人工检查
```

## 2. Finding 过滤策略

### 2.1 过滤不是删除

每条原始 finding 必须进入以下一种状态：

- `retained`：进入主展示列表；
- `collapsed`：低优先级，进入折叠区域；
- `duplicate`：与另一条 finding 重复；
- `unresolved_location`：问题可能有意义，但无法可靠定位；
- `invalid`：结构不合法或没有实际检查内容；
- `limited`：超过数量上限，暂不展示。

所有状态都保留 finding 原文、分类原因和来源运行 ID。不能像当前逻辑一样把原 finding 删除后只留下通用 warning。

### 2.2 基础有效性检查

以下 finding 视为结构有效：

- `finding_id` 可生成稳定替代值；
- `issue_type` 属于允许枚举；
- `reason` 是非空、简短内容；
- scope 与定位字段匹配；
- suggestion 类型的 `suggested_value` 必须非空；
- uncertain item 可以没有 suggested_value；
- severity、confidence 使用允许枚举。

以下情况进入 `invalid` 或改为 uncertain item：

- reason 为空或只有“请检查”等无信息文本；
- suggestion 的 suggested_value 为空；
- observed_value 与 suggested_value 完全相同；
- 模型返回完整数据表、长篇解释或与输入无关内容；
- finding 声称修改、删除或补造原始数据。

### 2.3 科研语义过滤

MVP 应采用保守规则：

- 某个可选字段全部为空，不自动视为错误；
- `replicate_group` 或 `replicate_index` 为空，只有存在明确重复证据时才报告；
- 单位缺失只有在字段预期需要单位时才报告；
- 没有实验设计上下文时，不判断处理组合是否合法；
- 没有合理范围时，不把数值大小直接判断为异常值；
- `[模糊字符]`、`?`、非数值字符进入数值字段等确定性问题优先保留。

### 2.4 去重规则

单元格 finding 去重键：

```text
(issue_type, row_index, column_name, normalized_observed_value)
```

行级、列级和全局 finding 去重键：

```text
(scope, issue_type, column_name, normalized_reason)
```

规则：

- 相同单元格的不同 issue_type 不能合并；
- 相同问题重复返回时保留 severity 更高者；
- severity 相同时保留 confidence 更高者；
- 两者仍相同时保留信息更完整者；
- 被合并 finding 的 finding_id 记录在 `duplicate_ids` 中。

### 2.5 数量限制

建议普通页面主列表目标上限为 12 条：

- high：全部保留，不受上限限制；
- medium：最多 8 条；
- low：最多 4 条并默认折叠；
- 无法定位项：主区域只显示一条汇总，详情折叠显示。

数量限制在去重后执行。被限制的项目仍保存为 `limited`，页面显示“另有 N 条低优先级提醒”。

## 3. Severity 生成规则

### 3.1 定义

severity 表示“问题如果属实，对科研数据使用的影响”，不是 AI 的确定程度。

| 等级 | 判断标准 | 典型问题 |
|---|---|---|
| `high` | 可能导致样品错配、数据不可解析或明显错误结论 | 关键样品编号缺失、数值字段无法解析、字段错列、整行缺失 |
| `medium` | 数据仍可保留，但需要人工确认后使用 | 模糊字符、处理编号结构异常、重复索引冲突、单位冲突 |
| `low` | 不阻止数据使用的格式或信息提醒 | 单位未说明、显示格式不统一、非关键元数据缺失 |

### 3.2 issue_type 默认映射

| issue_type | 默认 severity |
|---|---|
| `missing_value` | medium；关键字段为空时 high |
| `type_mismatch` | high |
| `identifier_pattern` | medium；主索引无法使用时 high |
| `unit_inconsistency` | medium |
| `replicate_inconsistency` | medium |
| `numeric_format` | medium；完全无法解析时 high |
| `possible_outlier` | medium |
| `unresolved_character` | medium；关键编号或数值时 high |
| `other` | low |

本地可靠性层应根据字段角色做有限校正，但不得仅凭 AI reason 任意提高等级。

### 3.3 模型与本地规则分工

- Prompt 要求模型返回 severity；
- 本地代码验证枚举，非法值回退为 `medium`；
- 确定性规则可以提高或降低 severity；
- 调整前后值都写入日志，例如 `model_severity` 和 `effective_severity`；
- UI 和后续逻辑使用 effective_severity。

## 4. Confidence 使用方式

confidence 表示模型对 finding 是否成立的确信程度。

### 4.1 允许值

- `high`：输入中有直接、明确证据；
- `medium`：存在较强模式依据，但仍需人工确认；
- `low`：候选合理，但依据不足或存在多种解释。

### 4.2 不允许的用途

confidence 不得：

- 自动覆盖 observed_value；
- 自动接受 suggested_value；
- 删除实验行或字段；
- 决定 finding 是否被永久丢弃；
- 替代 severity。

### 4.3 展示和排序

排序优先级建议为：

```text
severity > 是否成功定位 > confidence > row_index
```

- high severity 即使 confidence=low 也必须展示；
- low severity 且 low confidence 可进入折叠区；
- 对 suggestion，confidence=low 仍允许显示建议，但必须明确是低置信度；
- 完全没有合理候选时 suggested_value 应为空并归入 uncertain item。

## 5. Row / Field 定位要求

### 5.1 必填定位字段

cell scope finding 必须包含：

- `row_index`：1 起始，指向当前 Extraction 行；
- `column_name`：必须是 `ColumnInfo.internal_name`；
- `observed_value`：与目标单元格原始值一致；
- 可选 `row_key`：样品编号等稳定行键；
- 可选 `location_text`：供人工阅读的自然语言位置。

row scope 必须有 row_index；column scope 必须有 column_name；global scope 不应伪造行列。

### 5.2 定位校验顺序

1. 检查 scope；
2. 检查 row_index 是否在 1 到总行数之间；
3. 检查 column_name 是否属于 Extraction 字段或允许的行元数据；
4. 读取实际 observed_value，禁止信任模型重复返回的原值；
5. 如果有 row_key，验证行号与行键是否一致；
6. 只有唯一匹配时才允许使用 row_key 恢复行号；
7. 无法唯一定位时设置 `location_status="unresolved"`，保留原 finding。

### 5.3 location_status

建议允许：

- `resolved`：行列已验证；
- `recovered`：通过唯一 row_key 恢复定位；
- `ambiguous`：存在多个可能位置；
- `unresolved`：无法定位；
- `global`：合法的全局 finding；
- `unvalidated`：旧数据或尚未处理。

模型只能提供候选位置，本地可靠性层决定最终 location_status。

### 5.4 字段别名

Prompt 必须提供合法 internal_name 列表。MVP 不建议自动接受任意别名。若需要兼容，可建立明确映射：

```text
显示名 → internal_name
```

无法唯一映射时标记 unresolved，不能猜测字段。

`replicate_group` 和 `replicate_index` 应作为允许的行级元数据单独处理，不要求出现在 columns 中。

## 6. Prompt 约束方案

### 6.1 输入约束

Prompt 明确提供：

- 总行数；
- 合法 column_name 列表；
- 每行 row_index；
- observed_values；
- replicate 元数据；
- 用户提供的可选实验上下文。

模型不得根据原图重新识别，因为 Validation 输入中没有图片。

### 6.2 输出约束

要求每个 finding 返回：

```json
{
  "finding_id": "validation-0001",
  "scope": "cell",
  "row_index": 5,
  "column_name": "treatment_name",
  "observed_value": "原始值",
  "issue_type": "unresolved_character",
  "severity": "medium",
  "confidence": "low",
  "reason": "一句简短中文原因",
  "suggested_value": null
}
```

约束：

- 顶层仍只包含 warnings、suggestions、uncertain_items；
- suggestion 的 suggested_value 必须非空且不同于 observed_value；
- 没有候选值时必须进入 uncertain_items；
- reason 最多一句，建议限制字符数；
- 只使用给定 column_name；
- 不输出完整数据副本或分析过程；
- 最多输出 12 条 finding；
- 优先 high，再输出 medium；low 只在数量允许时输出；
- 未提供设计依据时，不检查数值范围、合法组合或预期重复次数；
- 同一问题不得重复输出。

### 6.3 warnings 约束

warnings 仅用于无法绑定到具体 finding 的全局问题，例如：

- 输入没有任何数据行；
- 所有字段定义缺失；
- 数据整体无法执行某类检查。

禁止把每个定位失败 finding 转成单独 warning。模型产生的定位失败项目仍应作为结构化 uncertain item 返回。

### 6.4 本地二次约束

不能只依赖 Prompt。Python 可靠性层仍需：

- 验证 JSON 类型和枚举；
- 重新绑定 observed_value；
- 计算 location_status；
- 检查 suggestion 非空；
- 去重、排序和限量；
- 保存所有原始 findings。

## 7. UI 展示优先级

本步骤只设计展示，不要求立即修改页面。

### 7.1 页面顺序

1. 高风险且已定位；
2. 高风险但无法定位；
3. 中风险且已定位；
4. 中风险但无法定位；
5. 低风险折叠区；
6. 被去重、被限量和原始日志仅在开发模式查看。

### 7.2 用户可见信息

每条主 finding 显示：

- 严重程度：高 / 中 / 低；
- 行号和中文字段名；
- 原始观察值；
- 问题原因；
- AI 建议值（如有）；
- 置信度；
- 定位状态。

用户不需要看到内部 finding_id、internal_name 或 suppression_reason，除非打开高级信息。

### 7.3 数量摘要

建议显示：

```text
模型原始发现：24
去重后：14
当前展示：10
无法定位：2
低优先级折叠：4
```

避免用 24 个相同 warning 卡片占满页面。

### 7.4 不改变确认流程

Step 2 不自动把 Validation suggestion 接入 final_value。未来即使允许用户接受建议，也必须继续保持 observed_value、suggested_value 和 final_value 分离。

## 8. 测试方案

### 8.1 单元测试

#### 结构与兼容

- 旧 finding 缺少 severity/location_status 时使用默认值；
- 非法 severity、confidence 和 scope 被安全归一化；
- suggestion 缺少 suggested_value 时转为 uncertain item；
- observed_value 始终从 Extraction 读取。

#### 定位

- 合法 row_index + column_name → resolved；
- 行号越界 → unresolved；
- 未知字段 → unresolved；
- replicate 元数据 → 合法定位；
- row_key 唯一恢复 → recovered；
- row_key 多重匹配 → ambiguous；
- 定位失败后原 finding 仍存在。

#### 去重与限量

- 完全相同 finding 只展示一条；
- 同一单元格不同 issue_type 均保留；
- high severity 不被数量限制隐藏；
- medium/low 按配额进入 collapsed 或 limited；
- 原始数量、重复数量和限制数量统计准确。

### 8.2 Prompt 协议测试

- Prompt 包含合法字段列表和总行数；
- Prompt 不包含图片或完整 raw_text；
- 明确 suggestion 必须有建议值；
- 明确最多 12 条；
- 明确缺少实验上下文时不得猜测；
- 输出字段与当前解析器兼容。

### 8.3 Mock 回归

构造包含以下内容的固定 ExperimentResult：

- 一个明确模糊字符；
- 一个关键缺失值；
- 一个合法空 replicate；
- 一个重复 finding；
- 一个越界行号；
- 一个未知字段；
- 15 个低优先级提醒。

验证过滤、定位、排序和限量完全确定，不调用 API。

### 8.4 真实模型质量测试

使用 3 至 5 份脱敏 Extraction 固定结果，每份至少运行 3 次，记录：

- 原始 finding 数量；
- 有效 finding 比例；
- 定位成功率；
- 重复率；
- 无意义 warning 数量；
- suggestions 中非空建议比例；
- 三次运行的 finding 复现率；
- token、输出长度和耗时。

人工把每条 finding 标记为有效、可能误报或无意义，不能只凭数量判断质量。

### 8.5 回归标准

建议 MVP 验收目标：

| 指标 | 目标 |
|---|---:|
| 原始 finding 可追溯率 | 100% |
| 每条 finding 有 location_status | 100% |
| 可定位 finding 定位成功率 | ≥ 90% |
| suggestion 非空 suggested_value 比例 | 100% |
| 重复 finding 进入主列表比例 | 0% |
| high severity 被隐藏数量 | 0 |
| Validation 修改 Extraction 次数 | 0 |

真实有效率和误报率暂不设置夸大的目标，应先取得人工标注基线。

## 9. 最小实施顺序

1. 在 Validation Service 中实现定位校验，并保留无法定位的原 finding；
2. 实现 suggestion/uncertain item 语义校验；
3. 实现 severity 本地归一化；
4. 实现稳定去重键和状态统计；
5. 实现 medium/low 数量限制，high 全部保留；
6. 最后调整 Prompt，使模型输出与本地规则一致；
7. 完成离线测试后，再用固定 Extraction 结果执行真实 API 质量对比。

这个顺序优先建立确定性的本地保护层，避免只依赖 Prompt 控制生成式模型。

## 10. 本阶段不做

- 不修改 Extraction；
- 不把 Validation 写入 ExperimentResult；
- 不自动接受 AI 建议；
- 不自动修改、删除或补造实验数据；
- 不实现多次调用投票；
- 不修改 Excel；
- 不开发异常值统计模型；
- 不提交 Git。
