# v0.2.2.3 Validation Reliability Layer 设计

## 1. 设计目标

Validation Reliability Layer（校验可靠性层）位于 Validation Provider 与页面展示之间，负责让 AI 检查结果可追踪、可定位、可筛选、可比较。

它不重新识别图片，不修改 Extraction 数据，也不自动接受 AI 建议。

```text
Extraction ExperimentResult（只读）
                ↓
        Validation Provider
                ↓
       原始 Validation 响应
                ↓
 Validation Reliability Layer
  日志 / 校验 / 定位 / 去重 / 限量
                ↓
        ValidationResult
                ↓
     UI 展示与未来 Excel 审计
```

主要解决四个问题：

- finding 原始记录未保留，标准化失败后无法追溯；
- 无法定位的 finding 被转换为大量通用 warning；
- finding 没有严重程度和数量限制；
- 同一输入多次调用的结果可能不同，缺少比较依据。

## 2. 核心边界

### 保持不变

- Extraction Prompt、Extraction Provider 和 `ExperimentResult` 的现有职责；
- Extraction 生成的 columns、observed_rows 和原始观察值；
- Validation 作为独立、可失败、可重新运行的步骤；
- AI 只能提出检查结果，不能写入最终实验数据；
- Validation 失败不能阻止人工确认和 Excel 导出。

### 可靠性层负责

- 保存 Validation 输入摘要、原始响应和解析结果；
- 校验 finding 的结构和定位；
- 保留无法定位的 finding，而不是丢弃；
- 统一 severity、去重、排序和数量控制；
-记录运行元数据，支持同一输入多次结果比较。

## 3. Validation 日志保存设计

### 3.1 日志分层

建议每次 Validation 生成一个 `ValidationRunLog`，包含四层信息：

1. **请求摘要**：Validation 输入的稳定摘要，不重复保存图片，也不保存密钥。
2. **模型原始响应**：模型返回的原始 content，供 JSON 解析和质量复盘。
3. **解析结果**：Provider 初次解析得到的 findings，尚未做绑定过滤。
4. **可靠性处理结果**：定位、去重、限量后的最终 ValidationResult。

建议结构：

```python
ValidationRunLog(
    run_id="validation-uuid",
    input_fingerprint="sha256...",
    provider="doubao",
    model="model-id-or-safe-alias",
    started_at="ISO-8601",
    finished_at="ISO-8601",
    duration_seconds=40.2,
    response_id="...",
    finish_reason="stop",
    token_usage={...},
    raw_response_content="...",
    parsed_finding_count=7,
    retained_finding_count=4,
    suppressed_finding_count=3,
    parse_status="success",
    error_type=None,
    error_message=None,
)
```

### 3.2 输入指纹

为了判断两次 Validation 是否检查了同一份 Extraction 结果，应对以下内容进行稳定序列化后计算 SHA-256：

- columns 的 internal_name、display_name 和单位；
- observed_rows 的行顺序和 observed_values；
- replicate_group、replicate_index；
- 可选 experiment_context。

指纹只用于匹配运行，不用于判断数据正确性。

### 3.3 保存范围与隐私

MVP 建议只保存在当前 Streamlit Session State：

- 不建立数据库；
- 不写入项目目录；
- 不记录 API Key、Authorization Header 或完整请求头；
- 默认不长期保存真实科研数据；
- 开发模式可让用户主动下载脱敏日志 JSON。

如果未来需要项目保存，应由用户明确开启，并说明保存位置和保留期限。

### 3.4 原始响应与用户页面

- 普通用户只看到整理后的 findings 和运行摘要；
- developer 模式可展开查看原始响应、解析状态和抑制原因；
- 解析失败时仍保存 raw response，以区分空响应、截断和格式错误；
- 原始响应不得自动写入 Excel 主数据表。

## 4. ValidationResult 扩展方案

### 4.1 保持独立

不建议给 `ExperimentResult` 增加 Validation 字段。`ValidationResult` 应继续独立存在，并通过 `input_fingerprint` 或页面 result_id 与对应 Extraction 结果关联。

### 4.2 建议扩展字段

```python
ValidationResult(
    warnings=[...],
    suggestions=[...],
    uncertain_items=[...],
    provider="doubao",
    status="completed",
    response_metadata={...},
    run_id="...",
    input_fingerprint="...",
    raw_findings=[...],
    suppressed_findings=[...],
    summary={
        "raw_count": 24,
        "retained_count": 10,
        "unresolved_binding_count": 3,
        "duplicate_count": 5,
        "limited_count": 6,
    },
    run_log=ValidationRunLog(...),
)
```

兼容策略：新增字段全部使用默认值。旧 Mock Provider 和旧结果仍可创建、展示和测试。

### 4.3 warnings 的处理

当前 `warnings: list[str]` 可保留用于全局提醒和兼容，但不再承担“无法定位 finding”的全部信息。

无法定位的 finding 应继续保存在 `raw_findings` 或 `suppressed_findings`，并带有：

- `binding_status="unresolved"`；
- `suppression_reason="invalid_column"` 等机器可读原因；
- 原始 reason、observed_value 和 suggested_value。

页面可以显示一条汇总 warning，例如“有 3 项暂时无法定位”，而不是生成 3 条重复的通用 warning。

## 5. Severity 字段设计

### 5.1 等级

建议在 `ValidationFinding` 中新增：

```python
severity: str = "medium"
```

只允许：

| severity | 含义 | 示例 |
|---|---|---|
| `high` | 可能导致样品对应错误、数据无法使用或结论明显错误 | 关键编号缺失、数值字段无法解析、同一行字段错位 |
| `medium` | 数据可保留，但必须人工确认 | 模糊字符、处理编号结构异常、重复索引冲突 |
| `low` | 非阻断的格式或信息完整性提醒 | 单位未说明、显示格式不统一 |

### 5.2 severity 与 confidence 分离

- severity：问题如果属实，影响有多大；
- confidence：AI 对该 finding 是否成立有多确定。

例如“关键样品编号可能读错”可以是 `severity=high`、`confidence=low`。低置信度不能让高风险问题消失，也不能授权自动修改。

### 5.3 决策矩阵

| severity | confidence | 默认处理 |
|---|---|---|
| high | 任意 | 展示并要求人工检查 |
| medium | high/medium | 正常展示 |
| medium | low | 展示为不确定项 |
| low | high | 折叠展示 |
| low | low | 可被数量限制抑制，但保留日志 |

Provider 返回不合法 severity 时，可靠性层统一降级为 `medium`，并记录结构警告。

## 6. Finding 定位字段设计

### 6.1 目标

定位必须使用稳定的内部字段，而不是依赖“第 5 行左侧”等自然语言。建议扩展：

```python
ValidationFinding(
    finding_id="...",
    scope="cell",
    row_index=5,
    column_name="treatment_name",
    observed_value="...",
    issue_type="unresolved_character",
    reason="...",
    suggested_value="...",
    confidence="low",
    severity="medium",
    row_key={"number": "5"},
    column_display_name="处理名称",
    location_text="第5行处理名称",
    binding_status="resolved",
    binding_error=None,
    source="model",
)
```

### 6.2 字段职责

- `row_index`：当前 Extraction 结果中的 1 起始行号；
- `column_name`：必须使用 column.internal_name；
- `row_key`：辅助防止页面重新排序后定位错误，可保存样品编号等稳定键；
- `column_display_name`：仅供中文展示，不参与绑定；
- `location_text`：保留模型自然语言位置，作为人工兜底；
- `binding_status`：`resolved`、`unresolved`、`ambiguous`、`global`；
- `binding_error`：例如 `row_out_of_range`、`unknown_column`、`row_key_mismatch`。

### 6.3 绑定顺序

1. 验证 scope；
2. 验证 row_index 范围；
3. 验证 column_name 是否在 Extraction columns 中；
4. 如果有 row_key，检查它是否与该行一致；
5. 如果行号失效但 row_key 唯一，可恢复定位并标记恢复来源；
6. 无法唯一定位时保留 finding，标记 `unresolved`，禁止猜测绑定。

`replicate_group` 和 `replicate_index` 属于行级元数据，应明确加入允许定位的元数据字段集合，避免被当作未知 column。

## 7. 输出数量限制策略

### 7.1 原则

数量限制只影响默认展示和返回给普通用户的主列表，不能删除原始模型 findings。所有被去重或抑制的项目仍保存在日志中。

### 7.2 处理顺序

```text
原始 findings
  ↓ 结构校验
有效 / 未定位 / 无效结构
  ↓ 去重
  ↓ severity 与 confidence 排序
  ↓ 配额限制
主展示 findings + suppressed_findings + 汇总
```

### 7.3 去重键

单元格 finding 使用：

```text
(issue_type, row_index, column_name, normalized_observed_value)
```

列级和全局 finding 使用：

```text
(scope, issue_type, column_name, normalized_reason)
```

同一单元格存在多个不同问题类型时不得合并。

### 7.4 MVP 配额

建议主列表最多 12 条：

- high：全部保留，不受总量截断；
- medium：最多 8 条；
- low：最多 4 条；
- 未定位：主页面最多显示 3 条，其余折叠汇总。

如果 high 已超过 12 条，应全部展示，并明确提示“高风险问题较多”。不能为了满足总数限制隐藏高风险 finding。

排序顺序：severity、是否已定位、confidence、row_index、column_name。

### 7.5 Prompt 与本地限制双层控制

- Prompt 要求最多返回固定数量的高价值 findings，以减少 token 和随机噪声；
- Python 可靠性层再次去重和限量，防止模型不遵守要求；
- 两层都不能修改 Extraction observed_value。

## 8. 随机波动处理

本阶段不建议自动多次调用并投票，因为会增加费用和等待时间。先提供可比较能力：

- 相同 input_fingerprint 的运行按 run_id 分开保存；
- 比较 finding 的稳定键，而不是比较模型生成的 finding_id；
- 统计重复出现次数和最近出现时间；
- UI 可显示“本次 AI 检查结果可能存在波动”，但不自动合并多次结果；
- 只有用户主动重新运行时才产生新调用。

未来若引入多次校验，可增加 `occurrence_count` 和 `stability_score`，但不能把稳定出现等同于事实正确。

## 9. 对现有模块的影响

### 9.1 UI

短期不需要改变现有主要布局，只需：

- warnings、suggestions、uncertain_items 继续分区；
- 增加 severity 中文标签和排序；
- 将 low 和未定位项折叠；
- 显示“原始数量、展示数量、被去重/抑制数量”；
- developer 模式显示 run_id、模型元数据和原始响应日志；
- Validation 失败或日志缺失仍不影响 Extraction 和 Excel。

### 9.2 Excel

v0.2.2.3 最小实现可以不修改 Excel。

未来若导出 Validation 审计信息，建议新增独立“AI数据检查”工作表，包含 finding_id、severity、位置、原始值、建议值、原因、绑定状态、用户决策和 run_id。不要改变“整理后数据”工作表，也不要把未经确认的建议写入最终数据。

### 9.3 ExperimentResult

不建议修改。Extraction 结果继续是只读输入，ValidationResult 独立保存并通过 input_fingerprint 关联。

### 9.4 ValidationResult

需要向后兼容地增加日志、severity、定位状态和统计摘要。新增字段均应有默认值，使 Mock、旧测试和旧 Session State 不立即失效。

### 9.5 Provider

ValidationProvider 接口可保持不变。真实 Provider 负责返回原始解析结果和 API 元数据，可靠性层负责本地标准化。不同模型不应各自实现一套去重、定位和数量限制规则。

## 10. 最小实现步骤

### Step 1：保留原始结果

- 新增 ValidationRunLog；
- 给 ValidationResult 增加 run_id、input_fingerprint、raw_findings、suppressed_findings 和 summary；
- Provider 保存脱敏响应元数据与原始 content；
- 增加旧结果兼容测试。

验收：任何解析或定位失败都能看到原始 finding，不再只剩通用 warning。

### Step 2：可靠定位

- 给 ValidationFinding 增加 severity、row_key、location_text、binding_status 和 binding_error；
- 建立允许字段和行级元数据集合；
- 修改标准化逻辑：无法定位时保留，不再删除；
- 增加越界行号、未知字段、元数据字段和 row_key 冲突测试。

验收：所有 finding 都能解释“定位成功或失败的原因”。

### Step 3：去重与限量

- 实现稳定去重键；
- severity 排序；
- 应用 high/medium/low 配额；
- 记录 duplicate_count 和 limited_count；
- 原始 findings 数量始终可追溯。

验收：24 条重复或低价值提醒不会全部占据主页面，高风险项不会被隐藏。

### Step 4：最小 UI 增强

- 展示 severity、定位状态和结果数量摘要；
- 折叠 low 与未定位项；
- developer 模式显示日志；
- 不增加接受建议或自动改值功能。

验收：页面更清楚，但 Extraction、人工确认和 Excel 行为不变。

### Step 5：质量回归

- 使用固定的 3 至 5 份脱敏 Extraction 结果；
- 每份结果运行至少 3 次；
- 统计有效 finding 比例、定位成功率、重复率、误报率和跨次复现率；
- 与当前 `24 / 0 / 1` 基线比较。

验收：可靠性提升由数据证明，而不是只看 warning 数量减少。

## 11. 建议验收指标

| 指标 | MVP 目标 |
|---|---:|
| 原始 finding 可追溯率 | 100% |
| finding 有明确 binding_status | 100% |
| 可定位 finding 的绑定成功率 | ≥ 90% |
| 重复 finding 进入主列表比例 | 0% |
| 无意义通用 warning 数量 | 显著低于当前基线 |
| high severity 被隐藏数量 | 0 |
| Validation 修改 Extraction 的次数 | 0 |

这些指标只衡量工程可靠性，不代表 AI 的科研判断准确率。有效发现率和误报率仍需人工标注样本评估。

## 12. 推荐实施范围

v0.2.2.3 建议只实现 Step 1 至 Step 3：日志、定位状态、severity、去重和限量。UI 只做最小展示适配，Excel 暂不修改。

这样可以先解决结果不可追溯和 warning 膨胀问题，同时保持 Extraction 完全不变、Validation 独立失败、AI 建议不自动覆盖实验数据。
