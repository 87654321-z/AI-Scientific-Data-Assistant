# v0.2.1 Extraction 全量 Benchmark 报告

## 一、测试目标

使用 `test_images/` 中原有10张真实科研图片，对比：

1. `legacy`：当前旧科研识别流程；
2. `extraction`：v0.2.1阶段1最小结构化提取流程。

每张图片记录：

- 成功或失败；
- `finish_reason`；
- 总耗时；
- API耗时；
- 输出长度；
- `structured_rows` 数量；
- 是否触发JSON自动重试。

本次只测试并生成报告，没有修改正式Prompt、Provider、UI、Excel、数据结构或README。

## 二、测试口径

### Legacy

调用：

```python
DoubaoProvider.process_images(images, stage="legacy")
```

Legacy的总耗时和API耗时包含：

- 首轮复杂科研识别；
- 当前已有的二次AI校验；
- 如果发生JSON错误，最多一次自动重试。

表格中的 `finish_reason` 和输出长度对应产生正式结构化数据的首轮响应。

### Extraction

调用：

```python
DoubaoProvider.process_images(images, stage="extraction")
```

Extraction只执行：

- 阶段1最小结构化识别；
- 必要时最多一次JSON重试。

不执行第二阶段AI校验。

### 180秒超时口径

本轮测试开始时，正式Provider没有配置请求超时。测试过程中出现：

1. Legacy第9张的一次请求等待超过30分钟且没有返回。该未完成调用被停止，随后测试从已保存的前8项继续；前8项没有重跑。
2. Extraction第10张最终在416.16秒后成功返回。

用户随后规定：

> 单次测试超过180秒记录为timeout。

此时20项原始调用已经全部完成，因此没有剩余图片需要重新调用。报告按以下两种口径同时统计：

- **原始API结果**：模型最终是否返回；
- **180秒测试口径**：超过180秒即视为timeout。

未来benchmark执行器应在客户端真正中止超过180秒的请求。本轮不修改正式Provider timeout逻辑。

## 七、JSON截断是否减少

### 与历史基线比较

| 模式 | JSON截断 |
|---|---:|
| 历史Legacy | 2/10 |
| 本轮Legacy | 0/10 |
| 本轮Extraction | 0/10 |

Extraction本轮没有出现任何 `finish_reason=length`。

但本轮Legacy也没有出现截断，说明模型输出存在随机波动。同一两张历史失败图片，本轮Legacy恰好成功：

- `_12_2.jpg`：本轮Legacy返回28行；
- `_13_2.jpg`：本轮Legacy返回22行。

因此不能仅凭一次10/10断言Legacy截断问题已经消失。

更可靠的证据是：

- Extraction平均输出长度减少31.3%；
- 两张历史截断图片在Extraction下再次完整返回；
- Extraction全部10张均为 `finish_reason=stop`；
- 没有任何Extraction请求需要JSON重试。

结论：

> Extraction显著降低了JSON截断风险，但需要多轮重复benchmark才能量化长期失败率。

## 九、timeout情况

### Legacy测试期间

Legacy第9张的一次请求等待超过30分钟，没有产生结果文件。

处理：

- 仅停止该未完成请求；
- 已完成前8张保留；
- 从第9张继续；
- 后续调用在121.55秒成功。

该事件说明：

- 当前正式Provider没有显式timeout；
- API或网络异常时可能无限等待；
- benchmark必须使用测试级超时。

### Extraction

第10张：

- 最终API返回成功；
- `finish_reason=stop`；
- 返回21行；
- API耗时416.12秒；
- 总耗时416.16秒。

按180秒规则应记录为timeout，而不是正常成功。

### 下一次benchmark建议

测试执行器应把每一个图片调用放入独立子进程：

```text
启动单图测试子进程
→ 最多等待180秒
→ 超时则终止子进程
→ 写入 timeout 记录
→ 继续下一张
```

不能只依赖Python线程取消，因为正在进行的同步网络请求未必能被线程安全终止。

这属于benchmark测试工具改进，不应在没有单独设计前直接修改正式Provider。

## 十、平均耗时分析

### 本轮原始结果

- Legacy平均总耗时：119.75秒；
- Extraction平均总耗时：97.52秒；
- Extraction平均快22.23秒；

### 去除Extraction超时样本

- 平均总耗时：62.12秒；
- 平均API耗时：62.09秒。

但去除超时后会产生幸存者偏差，因此不能把62.12秒作为全量平均速度。

### 与历史Legacy比较

- 历史Legacy平均：84.37秒；
- 本轮Legacy平均：119.75秒；
- 本轮Extraction平均：97.52秒。

不同轮次API速度波动明显。因此速度结论应优先使用同轮配对数据，并继续保留多轮benchmark。

## 十一、最终结论

### 1. Extraction成功率

- 模型最终返回口径：10/10；
- 180秒测试口径：9/10；
- JSON解析成功的10个响应全部为 `finish_reason=stop`。

### 2. 是否减少JSON截断

是。

- 历史Legacy：2次截断；
- 本轮Extraction：0次截断；
- 平均输出长度减少31.3%；
- 两张历史截断图片均完整返回。

但本轮Legacy也随机取得10/10，因此仍需重复测试确认长期失败率。

### 3. 是否存在数据行减少

存在1张Extraction行数少于本轮Legacy：

- 55行降为20行。

不过该图片历史Legacy结果曾在21～61行之间波动，不能据此认定Extraction漏行。另有2张Extraction行数增加。需要人工标注真实行数后才能判断。

### 4. 平均耗时变化

- 本轮Legacy：119.75秒；
- Extraction：97.52秒；
- Extraction原始平均快18.6%；
- 但有一次416秒超时，响应时间稳定性仍需解决。

## 十二、下一步建议

优先级1：

建立带180秒硬超时的独立benchmark执行器，并对同一10张图片重复运行至少3轮。

优先级2：

为3张行数不一致图片建立人工金标准：

- 图片真实记录行数；
- 每行所属列；
- 是否存在重复测量。

优先级3：

在不切换UI默认流程前，开始设计阶段2 Validation：

- 只返回不确定项和建议；
- 不复制完整observed_rows；
- 不修改Extraction数据；
- 阶段2失败时仍保留阶段1结果。

优先级4：

单独设计正式Provider的timeout和网络重试策略。不要把benchmark中的进程终止逻辑直接搬进业务代码。

## 十三、发布判断

Extraction已经证明可以显著降低JSON输出规模和截断风险，但目前不建议立即替换UI默认流程。

正式切换前至少需要：

1. 解决或明确处理180秒超时；
2. 人工核对3张行数不同图片；
3. 完成多轮稳定性测试；
4. 实现阶段2建议生成；
5. 验证人工确认和Excel流程仍然完整。
