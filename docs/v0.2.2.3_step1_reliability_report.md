# v0.2.2.3 Step 1 Validation Reliability 实施报告

## 1. 本步骤目标

本步骤为独立 Validation 流程增加最小可观测性：记录一次真实 AI 数据检查何时运行、使用哪个 Provider 和模型、耗时多久、是否成功，以及失败类别和安全的原始响应。

Extraction、ExperimentResult、UI 展示和 Excel 均保持不变。

## 2. 修改内容

### `core/validation_schemas.py`

新增 `ValidationRunLog`：

- `started_at`：UTC ISO-8601 开始时间；
- `finished_at`：UTC ISO-8601 完成时间；
- `provider`：Validation Provider 名称；
- `model`：模型 ID；
- `elapsed_seconds`：本次 Validation 总耗时；
- `success`：是否成功；
- `error_category`：稳定的机器可读错误分类；
- `error_message`：脱敏后的错误信息；
- `raw_response`：脱敏后的模型原始响应。

`ValidationFinding` 新增默认字段：

- `severity="medium"`；
- 保留原有 `confidence="low"`；
- `location_status="unvalidated"`。

`ValidationResult` 新增：

- `run_log: ValidationRunLog | None = None`。

所有新增字段均有默认值，旧代码使用原来的位置参数或关键字参数仍能创建结果。

### `providers/doubao_validation_provider.py`

- 成功时把运行日志放入 `ValidationResult.run_log`；
- API 或解析失败时，把运行日志附加到异常的 `validation_run_log` 属性后继续抛出原异常；
- 不吞掉异常，不改变原有中文错误提示；
- 记录成功响应的原始 content；
- 记录 Provider、模型、起止时间和总耗时；
- 错误分类支持 `timeout`、`network`、`api_error`、`json_parse` 和 `output_truncated`；
- API 失败的 attempt 也记录耗时和错误类别；
- 日志写入前使用当前 API Key 做精确遮蔽，替换为 `[REDACTED]`；
- 不记录请求头、Authorization Header 或 API Key 配置。

Provider 同时读取模型返回的 `severity` 和 `location_status`；缺失或非法值分别回退为 `medium` 和 `unvalidated`。

## 3. 兼容性设计

旧 Validation finding 不包含新字段时：

```text
confidence      → low
severity        → medium
location_status → unvalidated
```

旧 ValidationResult 不包含日志时：

```text
run_log → None
```

因此：

- Mock Validation 不需要立即修改；
- 现有 UI 不读取新字段，展示保持原样；
- Validation Service 仍返回相同的 warnings、suggestions 和 uncertain_items；
- Extraction 与 Excel 不依赖运行日志。

## 4. 日志读取方式

成功调用：

```python
validation_result.run_log
```

失败调用：

```python
try:
    provider.validate_result(result)
except Exception as error:
    run_log = getattr(error, "validation_run_log", None)
```

本步骤没有修改 UI，所以普通页面暂时不会显示这些日志。后续 developer 模式可以选择性展示安全字段。

## 5. 安全边界

- API Key 不作为日志字段保存；
- 原始响应和错误文本在写入日志前执行密钥遮蔽；
- 不打印运行日志；
- 不将日志写入磁盘或 Git；
- 日志当前只随结果或异常存在于运行内存中；
- 原始响应仍可能包含实验数据，因此不应默认公开展示或长期保存。

当前脱敏只保证配置中的完整 API Key 不进入日志。未来若要持久化日志，还需增加通用敏感字段过滤和用户授权。

## 8. 当前限制与下一步

本步骤只建立日志基础：

- 日志尚未持久化；
- UI 尚未显示日志；
- `location_status` 目前只是兼容字段，尚未实现可靠定位判断；
- severity 尚未参与排序和数量限制；
- Mock Provider 没有生成独立运行日志；
- 原始响应的通用隐私脱敏尚未实现。

下一步建议进入 Step 2：在 Validation Service 中实现 finding 定位状态，确保无法定位的 finding 仍被保留，并记录明确的失败原因。
