# DoubaoProvider 稳定性改进报告

## 一、改动范围

本轮只修改了：

- `providers/doubao_provider.py`
- 新增本报告 `docs/reliability_improvement_report.md`

没有修改 UI、Prompt 文件、Excel 结构、数据模型或 README。

## 二、稳定性改进内容

### 1. API 响应诊断

每次模型响应现在可以记录：

- response id
- finish reason
- prompt、completion 和 total token usage
- 输出字符长度
- API 调用耗时

诊断信息不包含 API Key。

### 2. 异常分类

当前可区分：

- 网络错误
- API 错误
- JSON 解析错误
- 输出截断

输出截断会结合以下信息判断：

- `finish_reason` 是否为 `length`
- 返回 JSON 是否缺少闭合符号
- JSON 解析失败位置是否接近返回末尾

### 3. 有限自动恢复

首轮内容无法转换为 JSON 时：

1. 保留第一次响应诊断。
2. 最多重新请求一次。
3. 重试时追加要求：

   > 上一结果不是完整 JSON，请仅返回完整 JSON，不要解释。

4. 第二次仍失败后停止，不再继续请求，并在异常中保留两次响应的诊断。

## 三、测试方法

使用原 benchmark 的同一组10张真实科研图片，按当前真实流程逐张执行：

```text
图片读取与布局检测
→ DoubaoProvider
→ 首轮视觉 API
→ JSON 解析
→ 二次校验（首轮成功时）
→ ExperimentResult
```

结果保存在：

- `test_images/benchmark_results_reliability.csv`

## 七、结论

### 1. 自动重试是否有效

本轮自动重试机制在工程上正常工作：

- 两张 JSON 失败图片都准确触发了一次重试。
- 没有无限重试。
- 两次响应的 ID、结束原因、token、长度和耗时均被记录。

但对本批测试图片，自动重试**没有提高最终成功率**。原因是重试仍要求模型生成几乎同样大的完整结果，只追加“返回完整 JSON”不足以降低输出规模。

### 2. JSON 截断是否减少

没有减少：

- 修改前：2张 JSON 不完整。
- 修改后：仍有2张最终失败。
- 修改后的4次相关响应全部明确返回 `finish_reason=length`。

新增诊断已经把原先的推测变成了确定证据：失败的直接原因是模型输出达到长度限制，而不是网络错误或本地 JSON 解析器误判。

### 3. 本轮改进的实际价值

虽然成功率仍为80%，但诊断能力已经明显提高：

- 能明确知道模型为何停止。
- 能看到每次响应消耗的 token。
- 能区分 API、网络、普通 JSON 错误和长度截断。
- 能证明普通重复请求不能解决当前问题。

## 八、下一步优化建议

### 优先级1：截断重试必须使用真正的紧凑输出

重试时不能继续要求完整输出所有详细不确定项。建议重试只返回：

- `columns`
- `observed_rows`
- 极简 `warnings`

详细 `uncertain_items` 放到后续校验请求。这样才能实际降低 completion token，而不只是再次强调“完整 JSON”。

### 优先级2：首轮优先保证 observed_rows

当前两次失败都发生在长 `uncertain_items` 数组中。应让首轮先安全返回全部原始数据行，再生成 AI 建议。科研数据的原始行完整性应高于一次性返回全部解释。

### 优先级3：针对大输出使用分块

当预计行数或列数较多时：

- 按区域或行范围分块识别。
- 每块返回短 JSON。
- 本地按原顺序合并。

这种方法会增加请求数量，但比整张图片结果在末尾全部丢失更可靠。

### 优先级4：设置明确超时并处理服务端波动

本轮出现单张约552秒的成功请求。建议后续：

- 为单次 API 设置合理超时。
- 对网络、429和5xx使用有限退避。
- 分别记录首轮和二次校验耗时。
- 评估二次校验是否必须对每张图片执行。

## 九、最终判断

本轮实现了“可诊断、有限重试、不会无限调用”的基础稳定性保护，但尚未解决长 JSON 的根本问题。

要把成功率从80%继续提高，下一步重点不是增加重试次数，而是**减少单次模型返回长度，并优先保证 observed_rows 完整返回**。
